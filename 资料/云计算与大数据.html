1.1 云计算定义与特征

NIST 定义：云计算是一种通过网络按需提供可配置计算资源（网络、服务器、存储、应用和服务）的模型，资源可以快速供给和释放，管理成本极低。

五大基本特征：

特征说明
按需自助服务用户无需人工交互即可自行配置和使用计算资源
广泛网络访问通过标准协议（HTTP/HTTPS）可从各种终端设备访问
资源池化计算资源以多租户模式服务于多个客户
快速弹性资源可快速伸缩，对用户而言资源近乎无限
可计量服务自动控制和优化资源使用，提供透明计量（Pay-as-you-go）

问题：判断以下场景分别属于哪种云服务模型：

(a) 某公司租用 AWS EC2 虚拟机部署自己的 Web 应用。
(b) 开发者使用 Google Firebase 直接构建移动应用后端，不需管理服务器。
(c) 销售团队使用 Salesforce CRM 系统管理客户关系。

答：

(a) IaaS — 用户租用虚拟机（基础设施），自己安装和配置操作系统、中间件和应用。
(b) PaaS — Firebase 提供了数据库、认证、存储等平台级服务，开发者只需关注业务代码。

1.4 虚拟化技术

虚拟化是云计算的基石，将物理资源抽象为逻辑资源，实现资源隔离与共享。

虚拟化类型原理代表技术
服务器虚拟化一台物理服务器运行多个虚拟机VMware ESXi、KVM、Hyper-V
存储虚拟化抽象物理存储，提供统一存储池Distributed Storage、SAN
网络虚拟化将物理网络抽象为虚拟网络VLAN、SDN、OpenFlow
容器化操作系统级虚拟化，共享内核Docker、containerd

虚拟机 vs 容器

对比维度虚拟机（VM）容器（Container）
虚拟化层次硬件级（Hypervisor）操作系统级（内核共享）
启动时间分钟级（需启动完整 OS）秒级/毫秒级
镜像大小GB ~ 数十GBMB ~ 数百MB
隔离性强（独立内核）弱（共享宿主机内核）
密度一台物理机运行数个~数十个一台物理机运行数百~数千个
📌 Hypervisor 类型
Type 1（裸机型）：直接运行在物理硬件上，性能高，如 VMware ESXi、KVM、Xen
Type 2（宿主型）：运行在操作系统之上，如 VirtualBox、VMware Workstation

问题：某云计算平台使用 KVM 提供虚拟机，使用 Docker 运行微服务。请分析这两种技术在资源隔离和性能开销上的区别。

答：

KVM 虚拟机：Type 1 Hypervisor，每个 VM 有独立内核，通过硬件辅助虚拟化（Intel VT-x/AMD-V）实现强隔离。性能开销约 5-10%，适合需要强安全隔离的多租户场景。

Docker 容器：共享宿主机内核，通过 namespace 实现资源隔离（PID、Network、Mount 等），通过 cgroups 限制资源使用。性能开销接近零，启动毫秒级，适合微服务和 CI/CD。

典型组合：在 KVM 虚拟机内部运行 Docker 容器，既享受硬件隔离保障，又获得容器化的敏捷性。

1.5 云计算的挑战

  • 安全与隐私：数据加密、访问控制、合规认证
  • 服务可用性：SLA（服务等级协议）、多可用区部署

2.2 Hadoop 生态系统

Apache Hadoop 是大数据处理的事实标准开源框架，核心组件包括：

2.2.1 HDFS（分布式文件系统）

  • 架构：Master-Slave 模式，一个 NameNode 管理元数据，多个 DataNode 存储数据块
  • 数据块：默认 128MB，每个块自动复制 3 份（跨机架）
  • 设计理念：一次写入、多次读取；适合大文件、流式访问
  • 优点：高容错、高吞吐、适合批处理
  • 缺点：不适合低延迟访问、小文件多时性能差、不支持文件修改
HDFS 读流程 Client → NameNode(获取块位置) → DataNode(并行读取数据块) → Client(合并)
HDFS 写流程 Client → NameNode(分配块) → 写入第一个 DataNode(流水线复制) → 第二、第三 DataNode → 确认

问题：一个 512MB 的文件存储在 HDFS 中，块大小 128MB，复制因子 3。请问：

(a) 文件被分成几个数据块？
(b) 总共占用多少物理存储空间？
(c) 如果有 6 个 DataNode，最多可容忍几个节点同时故障而不丢失数据？

答：

(a) 512 / 128 = 4 个数据块

(b) 4 块 × 3 副本 = 12 块，物理存储 = 512MB × 3 = 1.5GB

(c) 每个块的 3 个副本分散在不同节点（且尽量不同机架），最多可容忍同一块的 2 个副本同时故障。如果一个块分布在 3 个不同的 DataNode 上，那么这 3 个节点中最多坏 2 个，数据仍然可读。但如果某块的 3 个副本恰好都故障，则数据永久丢失。由于副本是跨机架分布的，实际容错能力通常可以容忍 N-1 个节点故障（如果 N ≥ 3 且副本分布得当）。

2.3 MapReduce 编程模型

MapReduce 是 Google 提出的分布式编程模型，分为两个阶段：

MapReduce 数据处理模型 Map 阶段：(k₁, v₁) → list(k₂, v₂)  — 并行处理输入键值对
Shuffle 阶段：按 key 分区、排序、合并，将相同 key 的数据发送到同一 Reduce
Reduce 阶段：(k₂, list(v₂)) → list(k₃, v₃)  — 聚合处理
📌 MapReduce 完整流程
① 输入分片：将输入文件分成固定大小的 split（默认与 HDFS 块对齐）
② Map 阶段：每个 split 由一个 Map 任务处理，输出中间键值对
③ Combiner（可选）：在 Map 端本地聚合，减少网络传输
④ Shuffle：分区、排序、归并，将相同 key 发送到同一 Reduce
⑤ Reduce 阶段：对每个 key 的 value 列表进行聚合计算
⑥ 输出：结果写回 HDFS

问题：用 MapReduce 实现 WordCount（单词计数），输入文件内容为 "hello world hello hadoop hello mapreduce"。请写出 Map 和 Reduce 函数的伪代码，并描述 Shuffle 后的中间结果。

答：

Map 函数：

map(key, value):
  // key: 行偏移量, value: 行内容
  words = value.split()
  for word in words:
    emit(word, 1)

Map 输出：(hello,1) (world,1) (hello,1) (hadoop,1) (hello,1) (mapreduce,1)

Shuffle 后（分区+排序+分组）：

(hadoop, [1])
(hello, [1,1,1])
(mapreduce, [1])
(world, [1])

Reduce 函数：

reduce(key, values):
  sum = 0
  for v in values:
    sum += v
  emit(key, sum)

最终输出：hadoop=1, hello=3, mapreduce=1, world=1

2.4 Spark

Spark 是 UC Berkeley AMPLab 开发的新一代分布式计算框架，相比 MapReduce 的主要优势：

对比维度MapReduceSpark
计算模式磁盘 I/O 频繁（每个阶段写磁盘）内存计算（RDD 缓存）
中间结果必须写 HDFS可缓存在内存中
迭代计算慢（反复读写磁盘）快（内存迭代）
延迟高（批处理）低（支持流处理）
API 简洁性仅 Map/Reduce 抽象RDD/DataFrame/Dataset 丰富
性能（典型）基线快 10~100x
Spark RDD（弹性分布式数据集） RDD 是 Spark 的核心抽象——不可变、分区、可并行操作的数据集合。
创建方式：从 HDFS 读取 / 从集合并行化 / 从其他 RDD 转换
操作类型：
  Transformation（惰性求值）：map, filter, flatMap, reduceByKey, join
  Action（触发计算）：count, collect, reduce, saveAsTextFile

问题：有如下 Spark 代码片段：

rdd = sc.textFile("hdfs://data.txt")    # RDD[String]
rdd2 = rdd.flatMap(lambda l: l.split())    # RDD[String]
rdd3 = rdd2.map(lambda w: (w, 1))    # RDD[(String, Int)]
rdd4 = rdd3.reduceByKey(lambda a,b: a+b)  # RDD[(String, Int)]
result = rdd4.collect()    # Action: 触发计算

(a) 指出哪些是 Transformation，哪些是 Action。
(b) Spark 为什么能比 MapReduce 快？

答：

(a) Transformation：flatMap、map、reduceByKey（惰性求值，不立即计算）
Action：collect（触发实际计算）

(b) Spark 比 MapReduce 快的主要原因：
① 内存计算：中间结果缓存于内存而非磁盘；
② DAG 调度：Spark 构建有向无环图（DAG）优化执行计划，减少不必要的 Shuffle；
③ 惰性求值：只有 Action 才触发计算，有机会做整体优化（如流水线执行）；
④ Task 启动快：基于线程而非进程。

2.5 YARN 资源调度

YARN（Yet Another Resource Negotiator）是 Hadoop 的资源管理层，将资源管理和作业调度分离：

  • ResourceManager（RM）：全局资源管理和调度
  • NodeManager（NM）：每个节点上的代理，管理容器
  • ApplicationMaster（AM）：每个应用一个，负责任务调度和监控
  • Container：资源抽象（CPU + 内存）

3.2 HBase

HBase 是 Google BigTable 的开源实现，运行在 HDFS 之上的分布式列族数据库。

  • 表结构：Row Key + Column Family + Column Qualifier + Timestamp + Value
  • 架构组件：HMaster（管理）、RegionServer（数据服务）、ZooKeeper（协调）
  • Region：表的水平分区，每个 RegionServer 服务多个 Region
  • 特点：稀疏存储、多版本（时间戳）、可扩展、随机读写

问题：某物联网平台需要存储百万级设备每秒钟上报的传感器数据（设备ID、时间戳、温度、湿度）。请设计 HBase 表结构，重点说明 RowKey 的设计策略。

答：

RowKey 设计：device_id + timestamp（反转）

原始方案：device_id + timestamp → 同一设备的所有数据连续存储，热点问题严重。

优化方案：device_id_hash(前缀) + device_id + timestamp。计算 device_id 的 MD5 前 2 位作为前缀，打散数据分布，避免 Region 热点。

表结构：

RowKey: md5_prefix(2) + device_id(8) + timestamp(8)
Column Family: "data"
  data:temp = 25.6
  data:humidity = 68

设计原则：

  • 加盐（Salting）：前缀散列消除热点
  • 尽量短：RowKey 在 HBase 中随数据一起存储，过长浪费空间
  • 时间戳反转：同设备最新数据在前（如果经常查询最新数据）

⚡ 四、流处理与实时计算

4.1 批处理 vs 流处理

维度批处理（Batch）流处理（Stream）
数据处理方式对静态数据集批量处理数据到达即处理
延迟分钟~小时级毫秒~秒级
数据范围全量数据当前窗口数据
典型框架MapReduce、Spark BatchSpark Streaming、Flink、Storm
适用场景报表生成、数据清洗实时监控、欺诈检测

4.2 Spark Streaming

  • 微批次架构：将实时流切分为小批次（如每秒一批），用 Spark 引擎处理
  • DStream：离散化流，本质上是一系列连续的 RDD
  • 窗口操作：滑动窗口（window）、滚动窗口（tumbling）

4.3 Flink

  • 真正的流处理：每条数据到达即处理，而非微批次
  • 事件时间（Event Time）：支持乱序事件处理，通过 Watermark 机制
  • Exactly-Once 语义：精确一次处理保证
  • 有状态计算：维护算子状态，支持故障恢复
对比Spark StreamingFlink
架构微批次（Micro-batch）真流（True Streaming）
延迟秒级（取决于批次间隔）亚秒级
Exactly-Once支持（通过 WAL 和事务输出）原生支持
事件时间处理支持（1.2+）原生支持，Watermark 完善
状态管理基于 RDD 的 Checkpoint分布式快照

🚢 五、云原生技术

5.1 云原生定义

云原生（Cloud Native）是一种构建和运行充分利用云计算模型优势的应用的方法论。核心包括：

  • 微服务（Microservices）：将单体应用拆分为小型独立服务
  • 容器化（Containerization）：用容器封装服务及其依赖
  • 容器编排（Orchestration）：自动部署、扩展和管理容器
  • DevOps：开发与运维一体化，CI/CD 自动化
  • 声明式 API：用描述性配置而非命令式操作

5.2 Kubernetes（K8s）

Kubernetes 是 Google 开源的容器编排平台，已成为云原生的事实标准。

核心概念作用

5.3 Serverless

  • 函数即服务（FaaS）：开发者只需编写函数代码，平台自动管理伸缩
  • 按需付费：按实际执行时间和资源计费，不运行不计费
  • 典型产品：AWS Lambda、Google Cloud Functions、阿里云函数计算
  • 适用场景：事件驱动型任务、Webhook、数据处理管道

6.2 高频简答题模板

IaaS / PaaS / SaaS 三者的区别？
从用户管理的层次区分：IaaS 提供虚拟机、存储等基础设施，用户管理 OS 以上所有内容；PaaS 提供运行时和中间件平台，用户只管理应用和数据；SaaS 提供完整软件服务，用户仅使用。口诀：IaaS 是租房，PaaS 是精装房，SaaS 是酒店。
MapReduce 的 Shuffle 阶段做了什么？
Shuffle 是连接 Map 和 Reduce 的关键阶段：① 分区（Partition）：根据 key 的哈希值将数据分到不同的 Reduce 任务；② 排序（Sort）：每个分区内按 key 排序；③ 归并（Merge）：将 Map 输出的多个溢写文件合并为一个；④ 复制（Copy）：Reduce 从各个 Map 节点拉取对应分区的数据。
Spark 为什么比 MapReduce 快？
① 内存计算：中间结果缓存于内存，减少磁盘 I/O；② DAG 优化：构建有向无环图，优化执行计划，减少不必要的 Shuffle；③ 惰性求值：Action 才触发计算，有机会做全局优化；④ 线程级 Task：启动开销远小于 MapReduce 的进程级 Task。
什么是 CAP 定理？NoSQL 如何权衡？
CAP 定理指出分布式系统最多同时满足三个中的两个：一致性（Consistency）、可用性（Availability）、分区容忍性（Partition Tolerance）。由于网络分区必然发生，实际是在 CP 和 AP 之间选择。HBase 选 CP（强一致），Cassandra 选 AP（最终一致），MongoDB 默认 CP（可配置）。
容器和虚拟机的区别？
容器共享宿主机内核（OS 级虚拟化），无需模拟硬件和启动完整 OS，因此启动快（秒级）、镜像小（MB级）、密度高。虚拟机通过 Hypervisor 模拟完整硬件，拥有独立内核，隔离性强但开销大（启动分钟级、镜像 GB 级）。安全要求高的多租户场景用 VM，微服务和 CI/CD 场景用容器。
HDFS 小文件问题及解决方案？
小文件过多会导致：① NameNode 内存压力大（每个文件/块元数据约 150B）；② MapReduce 任务过多（每个文件一个 split）。解决方案：① 合并小文件（SequenceFile / HAR 归档）；② 使用 HBase 管理小文件；③ 调整块大小和分片策略。
